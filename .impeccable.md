## Design Context

### Users
Open Design is used by makers and product builders who are generating, previewing, sharing, and deploying small web artifacts. In deployment flows they are usually task-focused: they need to paste credentials, choose a hosting target, verify the public URL, and move on without reading a long setup guide.

### Brand Personality
Precise, calm, and craft-oriented. The UI should feel like a dependable local creative tool: clear enough for non-infra users, but respectful of technical details such as API tokens, domains, and deployment status.

### Aesthetic Direction
Refined utilitarian product UI in a light theme. Prefer compact grouped panels, visible hierarchy, soft borders, and status badges over loud blocks or decorative effects. Deployment results should read as one cohesive publication state, not disconnected alert cards.

### Design Principles
- Put instructions beside the field they explain; avoid detached helper text that forces users to scan the whole modal.
- Preserve the user's mental model for domains: enter the subdomain prefix first, then choose the base domain.
- Show `pages.dev` and custom-domain URLs as sibling rows inside one deploy result block.
- Keep status feedback calm and explicit: ready, pending, protected, and failed states should be visible without dominating the form.
- Reuse existing tokens and interaction patterns; do not introduce flashy gradients, heavy shadows, or decorative chrome for utility workflows.

### Cloudflare Custom Domain Decision Notes
- Use Cloudflare Pages custom-domain bindings in addition to DNS CNAME records because Pages must attach and verify the hostname before it can serve the project as a supported production route; DNS alone is not enough.
- Communicate latency as a two-step publish flow: `pages.dev` can be ready first, while the custom domain remains pending until Cloudflare Pages reports it active and the URL is reachable. Check-link retries should keep that custom row pending rather than implying final success too early.
- Keep the first release intentionally narrow: no apex/root-domain migration, wildcard domains, multiple custom domains per artifact, external DNS providers, Vercel custom domains, or advanced domain policy.
- Compared with Vercel/Netlify flows that often separate domain binding from DNS verification, this UI keeps binding and DNS mutation in one Cloudflare-only guided path because the selected zone is already managed by Cloudflare.
